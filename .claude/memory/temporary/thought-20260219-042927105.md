# Feature 005 Planning: Rule and Reminder Graph Nodes - Architecture Design

_Thinking document created 2026-02-19T04:29:27.117Z_

## Thoughts

### 2026-02-19T04:29:37.913Z - Thought
TECHNICAL CONTEXT ANALYSIS:

Current state: Memory plugin indexes only files it owns (permanent/ and temporary/ directories). External files (CLAUDE.md, rules/*.md, agent MEMORY.md) are invisible to the graph despite influencing agent behaviour.

Key observations from codebase:
1. MemoryType enum (enums.ts): 6 types currently (Decision, Learning, Artifact, Gotcha, Breadcrumb, Hub)
2. IndexEntry interface (memory.ts): Has relativePath field - exploration notes suggest using sentinel path 'external/<id>' with new externalPath field for actual location
3. Sync workflow (sync.ts): Scans permanent/ and temporary/ directories only - needs extension point for external files
4. Embedding pipeline (embedding.ts): truncateForEmbedding() handles 6000 char limit - perfect for large CLAUDE.md files
5. Mermaid visualization (mermaid.ts): NODE_SHAPES and NODE_STYLES dictionaries - hexagon {{}} for decision, stadium ([]) for learning, etc.
6. Link.ts: Already at 507 lines - constitution warns against adding to it

Module structure exists: bulk/, cli/, core/, graph/, maintenance/, quality/, scope/, search/, suggest/, think/, types/
No external/ module yet - this is new infrastructure.

### 2026-02-19T04:29:47.227Z - Thought
CONSTITUTION CHECK - P5 (Simplicity & YAGNI):

Design decision: Create new external/ module vs extending existing modules?

Analysis:
- External file discovery has DISTINCT lifecycle from user-owned memories
- Discovery algorithm is complex (walk directory tree, resolve symlinks, filter vendor paths)
- Two separate type systems (rule kinds: claude-instructions | claude-local-instructions | rules-file; reminder kinds: agent-memory-summary | agent-memory-sub-file)
- Read-only semantics require guards in EVERY mutating command

Conclusion: New external/ module is JUSTIFIED under P5 because:
1. Separation of concerns: external file lifecycle != user memory lifecycle
2. Reuse maximised: embedding pipeline, graph structure, index structure unchanged
3. Complexity contained: all discovery logic isolated in one module
4. Testability: module boundary enables comprehensive TDD

NOT over-engineering - this is genuine architectural separation.

### 2026-02-19T04:29:52.434Z - Thought
TYPE SYSTEM DESIGN:

Question: Why two types (rule + reminder) instead of one generic 'context-file'?

Semantic rationale from exploration:
- RULE files: PRESCRIPTIVE - tell Claude HOW to behave (CLAUDE.md, rules/*.md)
- REMINDER files: DESCRIPTIVE - tell Claude WHAT it knows (agent MEMORY.md)

This distinction matters for:
1. Graph edges: 'governed-by' (memory → rule) vs 'reminded-by' (memory → reminder)
2. Visual distinction: hexagon for formal authority vs cylinder for persistent storage
3. Future filtering: 'show me decisions governed by constitution' != 'show me patterns agent-curator remembers'

Why NOT reuse Hub type?
- Hub = user-writable linking node that LIVES in basePath
- Rule/Reminder = read-only external files that REFERENCE into basePath
- Semantic pollution: overloading Hub corrupts its meaning

Decision: Two new MemoryType enum values is the honest model.

### 2026-02-19T04:30:04.641Z - Thought
INDEXENTRY EXTENSION STRATEGY:

Current IndexEntry fields: id, type, title, tags, created, updated, scope, agent, relativePath, severity

Proposed additions:
- externalFileKind?: ExternalFileKind
- externalPath?: string

Why optional fields?
- Backward compatibility: existing memories don't need these fields
- Type safety: presence of externalPath signals external file
- Structural compatibility: relativePath gets sentinel value 'external/<id>' for consistency

Alternative considered: Create separate ExternalIndexEntry interface
REJECTED because:
- Would require union types throughout codebase (IndexEntry | ExternalIndexEntry)
- Complicates search/filtering logic
- Violates simplicity principle
- Two optional fields is minimal extension

Content hash handling:
- Embeddings.json already has hash field in EmbeddingCacheEntry
- Content hash enables invalidation detection during sync
- No changes needed to embedding cache structure

### 2026-02-19T04:30:14.244Z - Thought
SYNC INTEGRATION POINT:

Current sync workflow (sync.ts lines 189-353):
1. Load files from permanent/ and temporary/
2. Add missing files to graph
3. Add missing files to index
4. Remove ghost nodes (no file)
5. Remove orphan edges (no target)
6. Remove orphan index entries
7. Remove orphan embeddings

Proposed extension:
AFTER step 7, add new step:
8. Discover and index external files (rules + reminders)

Why AFTER existing reconciliation?
- External files are additive - they don't invalidate existing memories
- Keeps existing sync logic untouched
- Failed external discovery doesn't corrupt user data

Implementation approach:


New command: memory index-context
- Lightweight: ONLY runs external file discovery
- Skips orphan reconciliation (assumes graph is healthy)
- Use case: User edits CLAUDE.md, wants quick refresh without full sync

### 2026-02-19T04:30:26.366Z - Thought
DISCOVERY ALGORITHM COMPLEXITY:

Rule discovery challenges:
1. Directory tree walking: cwd → home (multiple CLAUDE.md files possible)
2. Symlink resolution: Agent-memory dirs might be symlinked
3. Vendor filtering: Exclude node_modules/, .git/, dist/, build/
4. Scope determination: Above git root = global, within = project

ID generation scheme (from exploration):
- rule-project-claude-md (CLAUDE.md at project root)
- rule-ancestor-2-claude-md (CLAUDE.md 2 dirs up from cwd)
- rule-global-claude-md (~/.claude/CLAUDE.md)
- rule-project-security (.claude/rules/security.md)
- reminder-project-curator-memory (.claude/agent-memory/curator/MEMORY.md)

Determinism requirement: Same file MUST generate same ID across syncs
- Use stable path markers (ancestor-N, project, global)
- Canonical path resolution for symlinks
- Sorted enumeration of rules/ and agent-memory/ directories

Edge cases requiring handling:
- CLAUDE.md exists in both project root AND .claude/ → both indexed
- Multiple ancestor CLAUDE.md files → all indexed with ancestor-N prefix
- Agent directory with no MEMORY.md → skip gracefully
- Extremely large CLAUDE.md (>6000 chars) → truncateForEmbedding handles it
