# Exploration: v1.5.0 Memory Graph Enhancement Suite

**Created**: 2026-02-17
**Explorer**: Speckit Explorer Agent
**Status**: Ready for Specification

## Feature Intent

Four interrelated graph enhancement features that build upon the v1.4.0 agent-scoped memories
foundation. They group into two tracks:

- **Data enrichment track** (Features 2, 3, 4): Extend edge metadata with cosine similarity
  scores and LLM-verified relation types, with a command to backfill and promote verified
  relations onto existing edges.
- **Analysis tooling track** (Feature 1): A new `check-relevance` command that uses multi-factor
  scoring to suggest scope optimisations for memories, deferred from v1.4.0 Phase 3.

The data enrichment track features are tightly coupled to one another. The analysis tooling track
is largely independent and can be implemented in any order relative to the other track.

```
2. Similarity values on edges: Extend GraphEdge (structure.ts) and EdgeMetadata (edges.ts) with

--auto-link, store the computed cosine similarity score. Thread the match.similarity value from
the suggest-links scoring loop through to linkMemories() and storeCrossScopeEdge() calls.

3. LLM-based link type verification: Add --llm-type flag to `suggest-links --auto-link`. When
set, uses Ollama (chat_model from .claude/memory.local.md, defaulting to gemma3:4b) to verify
the inferred link type before writing the edge. Given source and target memory titles and content,
the LLM confirms or suggests a better relation label. The result is stored as `verifiedRelation?:
string` on the edge (separate field, not replacing label). Gracefully degrades if Ollama is
unavailable. Requires a new skills/memory/src/services/ollama.ts providing generate() and
isAvailable() — does NOT reuse the hooks package directly.

4. Edge update command: New CLI command `memory update-edge <sourceId> <targetId> [--similarity
<float>] [--relation <label>] [--verify]` for replacing stale values and backfilling missing
fields on edges created before these features. Implementation in new file
skills/memory/src/graph/link-update.ts (extracted from link.ts, which is at its size warning
threshold at 503 lines). The --verify flag invokes LLM verification on the relation label,
storing the result as verifiedRelation on the edge. The --apply flag (on update-edge) promotes
verifiedRelation to label and removes the verifiedRelation field entirely, leaving a clean edge
with no dangling staging fields. Final state after apply: { label: "superseded-by", similarity:
0.91 } — no verifiedRelation, no llmConfidence.

All features must follow TDD (Red-Green-Refactor), British English in all comments and
documentation, and Bun test framework patterns.
```

## Research Notes

### Architectural Approach

**Recommended**: Incremental extension of existing data structures and extraction of a new module
to keep `link.ts` within size limits. No new abstraction layers.

**Rationale**: The existing `GraphEdge` optional-field pattern (sourceScope, targetScope,
sourceAgent, targetAgent) already accommodates sparse edge metadata. Adding `similarity` and
`verifiedRelation` as optional fields is consistent and backward-compatible. `loadMergedGraph()`
and the edges utility functions remove the need for any new infrastructure to support
check-relevance.

**Alternatives Considered**:

- **Separate edge metadata store** (e.g., `edge-metadata.json` alongside `graph.json`): Pros —
  cleaner separation of concerns, avoids bloating graph.json. Cons — requires a second I/O
  operation for every edge read, introduces a synchronisation problem between graph.json and the
  metadata store if they diverge, and adds complexity for no concrete benefit at this scale.
  Rejected per P5 (YAGNI).

- **Shared Ollama package** extracted from hooks into a common module: Pros — eliminates
  duplication between hooks and skills. Cons — requires a monorepo-level refactor, adds a build
  dependency, over-engineering for two consumers. Rejected per P5 (YAGNI). Revisit at v2.x if
  more packages need Ollama access.

- **Replace `label` immediately on LLM verification** (no staging field): Pros — simpler state
  machine. Cons — destroys the original inferred label, making it impossible to audit or revert
  without re-running the suggest-links pipeline. Rejected in favour of the clean promotion
  lifecycle (stage → apply → clean).

---

### Technology Evaluation

**Recommended Libraries / Frameworks**:

- **Bun test runner** (`bun:test`): Already in use. All new tests use `mock.module()` pattern,
  not `vi.mock()`. See gotcha: `bun-test-mocking-requires-mockmodule-not-viimportactual`.
- **ollama-js** (already in `hooks/package.json`): Add to `skills/memory/package.json` as a
  direct dependency. The new `skills/memory/src/services/ollama.ts` wraps it with the same
  timeout/retry pattern as `hooks/src/services/ollama.ts`.
- **Existing `cosineSimilarity()`** in `skills/memory/src/search/similarity.ts`: Already
  normalised for use. No new similarity library needed.

**Alternatives Not Chosen**:

- `openai` or `anthropic` SDK for LLM verification: Adds an external dependency and API cost.
  Ollama is already available, free, and has a graceful-degradation path.
- Custom content-analysis scoring using NLP libraries: Overkill for the content analysis
  component (20pts). Simple keyword and length heuristics are sufficient per P5.

---

### Key Considerations

**verifiedRelation clean promotion lifecycle**:

The staging → apply → clean lifecycle is the most important design constraint to preserve across
all four features. The flow is:

```
suggest-links --auto-link --llm-type
  → edge created with { label: "inferred", similarity: 0.87, verifiedRelation: "superseded-by" }

memory update-edge <src> <tgt> --verify
  → edge updated with { ..., verifiedRelation: "superseded-by" }  (can be run independently)

memory update-edge <src> <tgt> --apply
  → edge becomes { label: "superseded-by", similarity: 0.87 }     (verifiedRelation removed)
```

`--apply` is a destructive-but-clean operation. It succeeds silently if `verifiedRelation` is not
present (idempotent no-op). It should print a summary of what changed rather than requiring a
preceding `--dry-run`.

**link.ts size limit**:

`link.ts` is at 503 lines. The warning threshold is 500, hard limit 1000. Extracting
`updateEdgeMetadata` (and related helpers) to `link-update.ts` is both a necessary refactor and
the right place to implement Feature 4. This extraction must be the first implementation task in
the Feature 4 phase, not deferred to the end.

**GraphEdge backward compatibility**:

`graph.json` files on disk will not have `similarity` or `verifiedRelation` fields on existing
edges. Since both are `optional`, existing graphs load cleanly without migration. Backfill is
opt-in via `update-edge`.

**Cross-scope edge constraint**:

`suggest-links --auto-link` is READ-ONLY for cross-scope edges (existing production constraint,
not a v1.5.0 decision). This means `--llm-type` and similarity threading only apply to same-scope
edges during `auto-link`. Cross-scope edges can be enriched after the fact via `update-edge`.

**Performance**:

`check-relevance` uses `loadMergedGraph()` which loads all requested scope graphs. For large
memory sets (hundreds of nodes), the content analysis scoring component (20pts) should avoid
loading full file content unless `--format detailed` is specified. The type, tag, and
connectivity components work from index data alone.

**Ollama timeout**:

For user-interactive CLI operations (not hooks), a 15-second timeout per LLM call is appropriate.
The hooks default is 30 seconds for a different context. Use `DEFAULT_TIMEOUT_MS = 15000` in the
new `skills/memory/src/services/ollama.ts`.

### Open Questions

1. Should `check-relevance --auto-move` require explicit `--confirm` to prevent accidental bulk
   moves, similar to the destructive CLI operation pattern used elsewhere in the project?

2. Should `similarity` be clamped to 0–1 at write time in `addEdge()`, or trusted to be in range
   from the caller? (Recommended: clamp defensively in `updateEdgeMetadata` and in the
   suggest-links threading path.)

3. Is `llmConfidence` worth storing on the edge before `--apply`? If stored, it must be removed
   on `--apply` alongside `verifiedRelation`. If not stored, the staging state is simpler.
   (Recommended: do not store `llmConfidence`; the presence of `verifiedRelation` is sufficient
   signal that LLM verification has run.)

### Implementation Sequencing

| Order | Feature | Rationale |
|-------|---------|-----------|
| 1st | Similarity on edges (Feature 2) | Smallest change, pure data enrichment, no new dependencies. Unblocks Features 3 and 4 to test against real similarity data. |
| 2nd | Edge update command (Feature 4) | Triggers the link.ts refactor (healthy codebase hygiene). Enables backfill of similarity on existing edges. Sets up the `--apply` promotion path needed by Feature 3. |
| 3rd | check-relevance (Feature 1) | Independent, largest surface area, deserves its own phase. No dependency on Features 2–4. |
| 4th | LLM verification (Feature 3) | Most experimental. Requires Ollama service decision resolved in Feature 4 setup. Most likely to be adjusted based on real-world usage. |
