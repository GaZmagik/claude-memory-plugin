## Summary

Replace the `cmdSummarize` stub in `suggest.ts` with a fully working LLM-powered summarisation command. The implementation introduces one new module (`skills/memory/src/summarize/summarize.ts`) that handles memory collection, context-window-aware chunking, map-reduce LLM summarisation, and graceful fallback when Ollama is unavailable. The CLI handler in `suggest.ts` is updated to delegate to this module. No new dependencies, no persistence, no abstraction layers beyond the module boundary already established by the `suggest/suggest-links.ts` pattern.

---

**Language/Version**: TypeScript (strict), Bun runtime (existing)
**Primary Dependencies**: All internal — `ollama.ts`, `core/list.ts`, `core/read.ts`, `cli/helpers.ts`, `cli/response.ts`, `core/agent-discovery.ts`
**Storage**: None — summaries are ephemeral CLI output; nothing is written to disk
**Testing**: Bun test runner with `vitest` compatible API (`vi.spyOn`, `describe`, `it`, `expect`)
**Target Platform**: Node/Bun CLI (existing plugin infrastructure)
**Performance Goals**: Single-chunk summarisation of ≤50 memories completes within 120s (one LLM call)
**Constraints**: No new npm dependencies; no abstraction layers around `generate()` or `isAvailable()`
**Scale/Scope**: Default limit of 50 memories; chunking activates above ~39,000 total content chars

## Phase 0: Research

All research was completed during the exploration phase. See [research.md](./research.md) for full findings.

**Key Decisions**:

| Decision | Chosen | Rationale |
|----------|--------|-----------|
| LLM service | `generate()` + `isAvailable()` from `ollama.ts`, direct | No wrapper — P5 compliance |
| Token estimation | Character count ÷ 4 heuristic | No new dependency; sufficient at 16k token scale |
| Chunking strategy | Map-reduce (map per chunk, reduce when >1 chunk) | Proven by `suggest-links --llm-type`; keeps each call within limits |
| Content truncation | 6,000 chars per memory at word boundary | Matches existing embedding gotcha — prevents context length failures |
| Module placement | `skills/memory/src/summarize/summarize.ts` | Mirrors `suggest/suggest-links.ts` pattern |
| Default timeout | 120,000ms | Between `quality --deep` (60k) and `suggest-links --llm-type` (300k) |
| Default limit | 50 | Fits single chunk at default 16k window; protects against unbounded I/O |
| Persistence | None | P5 — out of scope for v1.8.0 |

## Risks and Mitigation

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| Positional arg parsing confusion in tests | High | Medium | Gotcha documented in research.md and spec assumptions: `positional[0]` is the type/ID after command routing strips the command name. Test fixtures use `positional: ['decision']` not `positional: ['summarize', 'decision']`. |
| Content truncation gotcha (Ollama context length error) | High | High if not applied | Truncate each memory's content to 6,000 chars before accumulating into chunks — already established pattern. Export `MAX_MEMORY_CONTENT_CHARS = 6_000` constant for testability. |
| `readMemory()` failure mid-run aborts summarisation | Medium | Low | Wrap each `readMemory()` call in try/catch. Skip failed memories with stderr warning. Exclude skipped IDs from `memoriesIncluded`. |
| Empty LLM response (`generate()` returns `""`) | Medium | Low | Return empty summary block for that type/chunk. Command still succeeds. Tested explicitly. |
| `vi.mock()` used instead of `vi.spyOn()` in tests | High | Medium | All mocking uses `vi.spyOn(module, 'functionName')`. This is the Bun-compatible pattern used throughout the existing spec files (see `crud.spec.ts`, `suggest.spec.ts`). Do NOT use `mock.module()` here — existing test files use `vi.spyOn`. |
| Duplicate memory IDs when `--all-agents` merges scopes | Low | Medium | Deduplicate by ID before content loading — use a `Map<id, MemoryContent>`. |
| `discoverAgents()` requiring `projectRoot` and `globalRoot` | Low | Low | Pass `process.cwd()` and `getGlobalMemoryPath()` — same pattern used in `crud.ts`. |
| Stale stub tests blocking CI | Medium | Certain | The two existing `cmdSummarize` stub tests in `suggest.spec.ts` (`'returns stub response'` and `'accepts type positional'`) must be removed and replaced with real tests in Phase B. |

## Implementation Notes for Task Generator

The following constraints must be enforced during task generation:

1. **TDD ordering**: Within each phase, ALL test tasks appear before ALL implementation tasks. No interleaving.
2. **Mock pattern**: Use `vi.spyOn(module, 'function')` throughout — the existing codebase uses this pattern exclusively (confirmed in `crud.spec.ts`, `suggest.spec.ts`). Do NOT use `mock.module()`.
3. **No new npm dependencies**: `summarize.ts` uses only existing internal modules.
4. **Constants exported**: `CHUNK_BUDGET_RATIO`, `CHARS_PER_TOKEN`, `MAX_MEMORY_CONTENT_CHARS`, `DEFAULT_TIMEOUT_MS`, `DEFAULT_LIMIT` — exported from `summarize.ts` for test access.
5. **Security comments**: Add a security comment block at the top of `summarize.ts` documenting that scope paths are resolved via helpers (not user input), content is author-written (not executable), and IDs are validated by `readMemory()`.
6. **Stub removal**: The Phase B test task explicitly removes the two existing stub tests from `suggest.spec.ts` before adding real tests.
7. **Help entry test**: Phase D must include a test assertion that `ANALYSIS_HELP.summarize.flags` is non-empty/contains expected flag documentation.
