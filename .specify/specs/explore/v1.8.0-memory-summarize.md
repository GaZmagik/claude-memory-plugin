# Exploration: Memory Summarize Command (v1.8.0)

**Created**: 2026-03-07
**Explorer**: speckit-explorer
**Status**: Ready for Specification

---

## Feature Intent

The `memory summarize` command is currently a stub in
`skills/memory/src/cli/commands/suggest.ts` that returns "not yet implemented
(requires LLM integration)". The feature should transform the stub into a
working LLM-powered summarisation tool that digests stored memories into
human-readable rollups — either across all types at once, or scoped to a
single type (decision, learning, gotcha, artifact, etc.).

The primary use case is giving a Claude agent (or a human) a rapid orientation
to a project's or agent's memory corpus: what decisions have been made, what
has been learned, and what pitfalls exist — without having to read every
individual file. A secondary use case is MEMORY.md drafting: producing a
concise prose summary that can be injected into an agent's system prompt.

The feature must degrade gracefully when Ollama is unavailable, falling back to
a plain structured listing of titles and types. It must respect the configured
`context_window` to avoid overflowing the LLM's capacity, and must support the
same scope and agent flags that every other read command in the system
understands.

## Suggested Specify Prompt

Use this as the argument for `/speckit:specify`:

```
Implement the `memory summarize` command in the claude-memory-plugin (v1.8.0).
The command collects stored memories — filtered by optional type, scope, agent,
and tags — and produces LLM-generated prose summaries via the existing Ollama
service.

Actors:
- Claude agents and human operators who invoke `memory summarize` from the CLI.
- The Ollama service (optional dependency; must degrade gracefully when absent).

Actions:
1. Collect memories using the existing listMemories() function, applying
   filters: type, scope, agent, tags, limit.
2. Read the full content of each collected memory using readMemory().
3. If Ollama is unavailable, return a structured title-and-type listing as the
   fallback output (no LLM call).
4. When Ollama is available, chunk the memory corpus to stay within the
   configured context_window, then call generate() with a summarisation prompt.
5. Support three output modes controlled by a flag:
   - `--mode per-type` (default): Generate one summary block per memory type
     present in the filtered set.
   - `--mode overview`: Generate a single cross-type executive summary.
   - `--mode digest <id>`: Generate a detailed summary of a single memory
     identified by ID.
6. Emit a structured JSON response matching the existing CliResponse envelope
   (status, message, data) so callers can parse results programmatically.
7. Support all standard scope/agent flags:
   --scope, --agent, --include-shared, --all-agents, matching patterns from
   cmdList, cmdQuery, and cmdSearch.
8. Include a `memoriesIncluded` array in the response data listing all memory
   IDs that contributed to the summary.

Success criteria:
- `memory summarize` with Ollama available returns at least one prose paragraph
  per type present.
- `memory summarize` without Ollama returns a fallback listing with a clear hint
  that LLM is unavailable.
- `memory summarize decision` filters to decision-type memories only.
- `memory summarize --mode overview` returns a single cross-type paragraph.
- `memory summarize --mode digest <id>` returns a focussed summary of one memory.
- `memory summarize --agent <name>` summarises agent-scoped memories.
- `memory summarize --all-agents` summarises across all agent namespaces.
- Response data includes a `memoriesIncluded` array of all IDs that were
  summarised.
- Memory content that exceeds the context window is chunked; each chunk is
  summarised individually and the chunk summaries are merged in a second pass.
- All existing tests continue to pass.
- The stub in suggest.ts is replaced; no "not yet implemented" text remains.
```

Implement `memory summarize` for the claude-memory-plugin (v1.8.0) following

  collection abstraction needed.
- Token estimation: Use a simple character-count heuristic (÷ 4) rather than
  a token-counting library. This avoids a new dependency and is accurate enough
  for chunking decisions at the 16k token scale.

Architecture:
- Implementation lives in a new file: `skills/memory/src/summarize/summarize.ts`.
  This keeps summarise logic out of the CLI layer (same pattern as
  `suggest/suggest-links.ts`).
- The CLI handler `cmdSummarize` in `suggest.ts` replaces the stub by calling
  into this new module.
- No caching or persistence of summaries to disk — summaries are ephemeral CLI
  output. Adding a cache layer at this stage is premature abstraction.

Chunking strategy (map-reduce):
- Phase 1 (map): Split memory list into chunks whose total character count
  stays below `(context_window * 4 * 0.6)` — 60% of estimated capacity,
  reserving headroom for the prompt template and model output. Summarise each
  chunk independently via generate().
- Phase 2 (reduce): If more than one chunk was produced, call generate() again
  with all chunk summaries to produce the final merged summary. Single-chunk
  corpora skip Phase 2.
- This two-phase approach mirrors the map-reduce pattern established by
  suggest-links --llm-type and keeps each LLM call well within limits.

Timeout: 120_000ms per generate() call (between suggest-links' 300_000ms bulk
timeout and the default 15_000ms; appropriate for a summary workload).

Output modes (--mode flag):
- per-type (default): Group memories by MemoryType, summarise each group.
- overview: Flatten all types, produce one paragraph.
- digest: Accept a single memory ID as positional arg, summarise its content.

Fallback (Ollama unavailable):
- Return a structured listing of { id, type, title, tags } for each collected
  memory, with a `hint` field on the CliResponse explaining that LLM is
  unavailable and summarisation was skipped.

Flags to support (mirror cmdList / cmdQuery / cmdSearch patterns):
  [type]            Positional: filter by memory type
  --mode <mode>     per-type | overview | digest (default: per-type)
  --scope <scope>   Target scope
  --agent <name>    Agent namespace
  --include-shared  Include shared scopes (requires --agent)
  --all-agents      Summarise across all agent namespaces
  --tags <tags>     Comma-separated tag filter
  --limit <n>       Cap memory count before summarising (default: 50)
  --timeout <ms>    Override LLM timeout (default: 120000)

Response data includes a `memoriesIncluded` array listing all memory IDs that
contributed to the summary. No hard safety limit — the --limit default of 50 is
the soft guard; users who override it accept the consequences.

Help entry update:
- Expand the existing stub entry in
  `skills/memory/src/cli/command-help/entries/analysis.ts` with full flag

- Unit tests for prompt assembly.

- Integration tests for cmdSummarize using mock generate() responses.
- All tests use Bun test runner with mock.module() (not vi.mock()).

## Research Notes

### Architectural Approach

**Recommended**: Map-reduce summarisation via the existing Ollama `generate()`
function, implemented as a standalone module in `skills/memory/src/summarize/`.

**Rationale**: The project constitution mandates library-first design with no
unnecessary abstraction layers. The Ollama service already provides everything
needed (`generate`, `isAvailable`, configurable `context_window`). A new
`summarize/` directory mirrors the pattern of `suggest/suggest-links.ts` —
keeping business logic out of the CLI handler while avoiding a shared-utility
soup.

**Alternatives Considered**:

- **Option A — inline in suggest.ts**: Pros: zero new files. Cons: suggest.ts
  already handles two unrelated commands (suggest-links, summarize); growing
  it further violates single-responsibility and will push it toward the 500-line
  warning threshold. Rejected.
- **Option B — streaming output via Ollama stream API**: Pros: lower latency to
  first token. Cons: the CLI response envelope is JSON and does not support
  streaming well; streaming would require significant new plumbing. Rejected for
  v1.8.0.
- **Option C — persist summaries to disk as a new memory type**: Pros: summaries
  become searchable. Cons: premature abstraction; adds write complexity and a
  cache invalidation problem for a v1 feature. Rejected.

### Technology Evaluation

**Token estimation**:
- Character-count heuristic (chars ÷ 4) is accurate to ±20% for Latin text at
  the 4k–16k token scale. Sufficient for chunking decisions.
- Alternatives: `tiktoken` (OpenAI tokeniser, wrong model family),
  `llama-tokenizer-js` (adds a dependency). Neither is necessary at this scale.

**Chunking strategy**:
- The default `context_window` is 16 384 tokens. At 4 chars/token that is
  ~65 536 characters. The 60% budget gives ~39 000 characters per chunk —
  enough to fit 30–50 average memories (roughly 800 chars each) in a single
  chunk, meaning most real-world invocations will not need Phase 2 at all.
- For the reduce pass: chunk summaries are typically 200–400 tokens each, so
  even 20 chunk summaries fit comfortably in one final generate() call.

**Timeout**:
- suggest-links uses 300 000 ms for bulk LLM operations over many edges.
- The `quality --deep` command uses 60 000 ms for single-memory assessment.
- Summarise sits between these: 120 000 ms per generate() call is conservative
  but appropriate when the corpus may span many memories.

**Output format**:
- Prose is preferred over structured JSON for the `data.summary` field because
  the primary consumer is a human or Claude agent reading context. A hybrid
  approach (prose summary + metadata array listing the memory IDs that were
  included) gives programmatic access without sacrificing readability.

### Key Considerations

- **Performance**: listMemories() is index-backed (no file I/O per memory for
  the listing phase). readMemory() is one file read per memory for the content
  phase. With a default limit of 50, this is 50 sequential file reads — fast
  in practice, but the limit guard is important to avoid unbounded I/O on large
  corpora.
- **Security**: Paths are already validated in readMemory() (path traversal
  guard). No new surface area. The `--limit` flag prevents resource exhaustion.
- **Context window**: The 60% budget constant must be named (e.g.
  `CHUNK_BUDGET_RATIO = 0.6`) and documented — it is a tunable parameter, not
  magic.
- **Dependencies**: No new runtime dependencies. The feature uses only existing
  internal APIs.
- **Risks**:
  - If Ollama is slow, a large corpus summarisation can block for several
    minutes. The `--timeout` flag and the default 120 000 ms cap mitigate this.
  - If `readMemory()` fails for one memory (e.g. file deleted since indexing),
    the implementation should skip that memory and log a warning, not abort the
    whole summarisation.
  - The gotcha memory notes that `positional` arrays in CLI tests must be
    structured correctly (`positional: ['summarize']` not
    `positional: ['summarize', 'decision']` when type is a positional arg —
    confirm test fixtures match the actual parsed structure from `parseArgs`).
  - Security constraints for scope resolution should be documented in comments
    before implementation (per project gotcha on scope-before-implementation).

### Resolved Questions

- **Digest ID**: Positional argument — `memory summarize --mode digest my-memory-id`.
  Matches existing `memory read <id>` convention.
- **Memory ID listing**: Yes — response `data` includes a `memoriesIncluded` array
  listing all IDs that contributed to the summary, for auditability.
- **All-agents support**: Include `--all-agents` in v1.8.0 to summarise across all
  agent namespaces at once (matching `memory search --all-agents` pattern).
- **Safety limit**: Soft limit only — the `--limit 50` default is sufficient. No
  hard refusal or `--force` flag needed; users who override the limit accept the
  consequences.
